# 14 — Predicting a token from its generation time

[All exercises and impact guide](../README.md#what-an-attacker-actually-gains)

**Weakness:** [CWE-338](https://cwe.mitre.org/data/definitions/338.html) ·
**Before:** [vulnerable.c](vulnerable.c) · **After:** [fixed.c](fixed.c)

## Attacker control and objective

The attacker estimates the time at which a victim generated a token and
knows the generator's `rand()` implementation. The objective is to reproduce
a valid-looking token by enumerating a few possible seeds instead of searching
all token values. The victim uses the current time by default; the optional
seed argument lets the attacker reproduce candidates locally.

## How the attack works

1. A normal invocation seeds `rand()` with `(unsigned)time(NULL)`, in
   seconds, and prints the first result.
2. A caller who knows the generation time within a few seconds has only a
   small set of candidate seeds. Every process starts at the first PRNG output.
3. For each candidate second, the attacker calls the local copy with that
   explicit seed. The same seed and C library produce the same first output.
4. One candidate reproduces the victim's token. In a real reset workflow the
   attacker would need a verifier that accepts a candidate; this program has
   no reset endpoint. The lab harness compares strings only to prove prediction.

Merely seeding a larger noncryptographic generator from the same small time
window would not remove the small set of possible initial states.

## Run the attack and compare the patch

Use Bash from the repository root. These are local programs run as your
ordinary account. Rejection and sanitizer failures intentionally return nonzero;
run the commands individually or in a shell without `set -e`.

```sh
make -C exercises/c_security all
LAB_BIN=./exercises/c_security/build/14_predictable_token

# Victim: generate normally, with no attacker-supplied seed.
LAB_START=$(($(date +%s) - 2))
LAB_ISSUED=$("$LAB_BIN/vulnerable")
LAB_END=$(($(date +%s) + 2))

# Attacker: use only the estimated time window to generate candidates.
for LAB_SEED in $(seq "$LAB_START" "$LAB_END"); do
  LAB_GUESS=$("$LAB_BIN/vulnerable" "$LAB_SEED")
  printf 'candidate seed=%s %s\n' "$LAB_SEED" "$LAB_GUESS"
  # Instructor's local verifier, not information used to generate guesses:
  if [ "$LAB_GUESS" = "$LAB_ISSUED" ]; then
    printf 'LAB VERIFIER: candidate reproduces the issued token\n'
  fi
done

# The patched generator has no time-seed interface.
"$LAB_BIN/fixed"
"$LAB_BIN/fixed"
```

The candidate list contains `token=...` values, with at least one
`LAB VERIFIER: candidate reproduces the issued token` message when the
victim's clock stayed in the measured window. Exact seeds and tokens vary.
The candidate calculation uses the seed and algorithm, not `LAB_ISSUED`;
that variable is held by the harness solely to confirm the prediction.

Each fixed invocation prints `token=` followed by 32 hexadecimal digits
representing sixteen bytes. Different outputs alone do not prove security;
the relevant change is removal of the predictable seed and generator.

## What the attacker gains

**Demonstrated:** a short list that contains the token generated by the
vulnerable process, without using that token to compute the candidates.
There is no real account, reset request, session, or verifier to exploit in
this executable, so account takeover has not been demonstrated.

In a larger system, accepting one of these guesses as authorization could
expose the corresponding account operation. That would depend on the token
binding, validity window, guessing limits, and verifier. Prediction requires
the matching PRNG implementation; `rand()` sequences are not portable across
every C library. None of this changes the Linux UID or grants a shell.

## Why the patch stops this attack

Obtain sixteen bytes directly from Linux `getrandom()` with flags 0,
handling interruption, partial results, and failures, then encode the bytes
as hex. There is no clock-seeded `rand()` state for the attacker to enumerate.
Token expiry, secure storage, one-time use, and binding to an account remain
responsibilities of a surrounding system, not features of this generator.

## Verify the result

Confirm the time-window candidates reproduce the vulnerable output.
Check that fixed outputs have the expected 32 hexadecimal digits. Do not
add a probabilistic “all outputs must differ” test: collisions are possible,
and output appearance does not establish the quality of its source.

The [regression suite](../tests/test_exercises.py) checks the corresponding
fixed behavior. Run `make -C exercises/c_security test test-asan` for all exercises.
